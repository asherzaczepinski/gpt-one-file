Step 2 of the GPT · Splitting text into tokens

Byte Pair Encoding

A model can only do math on numbers. Byte pair encoding (BPE) is how the text of a million-character storybook becomes a list of numbers, by learning which chunks of text show up together most often and giving each chunk its own ID.

The problem it solves

Before the model can read "Once upon a time", each piece of that text needs an ID number, a bit like a locker number. The question is how big the pieces should be.

Piece sizeVocabularyLength of a storyCatch
One per letterTiny (~100)Very longThe model wastes effort re-learning that t-h-e spells "the" every time
One per wordHuge (100,000+)ShortAny word it has never seen, like a name or a typo, can't be written at all
BPE chunksYou pick (here 512)MediumCommon words become one token, and rare ones get spelled out from smaller pieces

The idea in one sentence: start with the 256 possible bytes, then over and over find the two neighbouring tokens that appear side by side most often and glue them into one new token, until you have as many tokens as you want.

Two phases: learning the rules, then using them

Training · once

Read 100,000 characters of stories. Repeat the count-and-glue loop 256 times. Write down every merge, in order. The result is a rulebook of 256 merges and a dictionary of 512 tokens.

→
Using · any time

Encode: turn any text into bytes, then replay the rulebook in the same order. Decode: look up each ID's bytes and stick them back together.

The seven functions

Each section below covers one function from step 2 of gpt.txt. There's no code, just what the function is for, what goes in, and what comes out.

  • 1read_textA file on disk → one long string of characters
  • 2new_tokenizerNothing → a blank tokenizer that knows only the 256 bytes
  • 3count_pairsA list of IDs → a tally of every side-by-side pair
  • 4mergeA list of IDs + one pair → a shorter list with that pair glued
  • 5tok_trainText + a target size → a rulebook of learned merges
  • 6tok_encodeAny text → a list of token IDs
  • 7tok_decodeA list of token IDs → readable text again

Where it goes next: the list of IDs from tok_encode is all the model ever sees. In step 3, each ID is swapped for a row of learned numbers (its embedding). At the very end, the model's guess for the next ID goes through tok_decode to become words again.

Function 1 of 7

read_text

Get the raw material. This function takes a file sitting on your disk and hands back everything in it as one long string of characters.

Goes in

A file path, such as stories.txt

→
Comes out

One string, 1,000,516 characters long

The goal

Everything that follows (counting pairs, learning merges, training the model) needs the text in memory as a single piece. read_text opens the file, reads every character from the first to the last, and returns it all at once.

How the input changes

Hardly at all, which is the point. On disk, the file is a stream of stored bytes. Afterwards it's a string that your program can slice, measure, and loop over. The stories begin like this:

Once upon a time, in a warm and sunny place, there was a big pit. A little boy named Tom liked to play near the pit. One day, Tom lost his red ball. He was very sad.↵ Tom asked his friend, Sam, to help him search for the ball. …

Nothing is cleaned up or removed:

  • Capitals stay capitals. "Once" and "once" are different text, and they'll end up as different tokens.
  • Punctuation stays. Commas, full stops, and quotation marks are all characters like any other.
  • Line breaks stay (shown here as ↵). They mark where one story ends and the next begins.

It reads the file as UTF-8. UTF-8 is the standard rule for storing letters as bytes. Plain English letters take one byte each, while something like "é" takes two. That's why the file is 1,000,910 bytes but only 1,000,516 characters: a few characters in the stories need more than one byte. This difference matters in new_tokenizer.

Where its output goes

The full string gets used twice:

  1. The first 100,000 characters go to tok_train to learn the merges. A tenth of the book is plenty to find out which letter pairs are common, and it's ten times faster.
  2. The whole million characters go to tok_encode afterwards, becoming the token IDs the model trains on.

Function 2 of 7

new_tokenizer

Set up an empty tokenizer. It starts out knowing only the 256 single bytes and has learned no merges yet.

Goes in

Nothing

→
Comes out

A tokenizer with two parts: an empty rulebook and a dictionary of 256 entries

The goal

Training needs somewhere to write down what it learns, and that somewhere has to start from a sensible base. The tokenizer is just two lists kept side by side:

The rulebook (merges)

Each rule says "when these two IDs sit next to each other, replace them with this new ID." It starts empty. By the end of training it holds 256 rules, kept in the order they were learned.

The dictionary (vocab)

For every ID, the exact bytes that ID stands for. It starts with 256 entries, one for each possible byte value from 0 to 255. By the end it holds 512.

Why start from bytes?

Computers store all text as bytes, which are numbers from 0 to 255. UTF-8 decides which bytes each character becomes:

CharacterIts bytesAs tokens
O79
n110
a space32
a line break10
é195, 169

So the first 12 characters of the stories, "Once upon a ", start out as 12 tokens:

Nothing can ever be unknown. Every possible text, in any language and with any emoji, is made of these 256 bytes. A word-based tokenizer gets stuck on a word it has never seen. This one can always fall back to spelling something out byte by byte.

What the dictionary looks like at the start

The ID and the byte value are the same number, so each entry simply points to itself:

IDStands for
0 … 31invisible control bytes (10 is a line break)
32a space
65 … 90A to Z
97 … 122a to z
128 … 255pieces of multi-byte characters like é
256 +empty for now. Training fills these in.

Function 3 of 7

count_pairs

Find out which two tokens sit next to each other most often. This is the "eyes" of BPE: it decides what is worth gluing together.

Goes in

A list of token IDs

→
Comes out

A tally: every neighbouring pair, and how many times it appears

The goal

To pick the next merge, BPE needs to know which pair is the most common. count_pairs slides a two-wide window along the list, one step at a time, and keeps a running count of each pair it sees.

A small example

Input: [1, 2, 3, 1, 2]. The window looks at each neighbouring pair in turn:

WindowPairTally so far
[1, 2], 3, 1, 2(1, 2)(1,2): 1
1, [2, 3], 1, 2(2, 3)(1,2): 1 · (2,3): 1
1, 2, [3, 1], 2(3, 1)(1,2): 1 · (2,3): 1 · (3,1): 1
1, 2, 3, [1, 2](1, 2)(1,2): 2 · (2,3): 1 · (3,1): 1

Output: (1, 2) appears twice, and the other pairs once each. A list of 5 IDs always has 4 neighbouring pairs.

On real text

The opening of the stories, "Once ", as bytes:

gives four pairs: O+n, n+c, c+e, and e+␣. Do the same across all 100,048 training bytes and you get 702 different pairs. These are the top six:

PairCountWhy it's common
3,542lots of words end in e: the, he, she, little, time
2,906words starting with t: the, to, they, then
2,896the, he, she, they, her
2,616and, played, said, wanted
2,167a, and, at, asked
2,014the, that, there, they

Notice that BPE never knew English. It found "the" hiding in these counts purely from statistics.

It only counts. It doesn't change anything. The list going in is left untouched. Deciding which pair wins and rewriting the list are jobs for tok_train and merge.

One subtlety: overlapping pairs

In [1, 1, 1], the window sees (1, 1) at positions 1–2 and again at 2–3, so it counts 2. But you can only glue one of them, since the middle 1 can't belong to both. The count is a good estimate of how useful a merge will be, not an exact one.

Function 4 of 7

merge

Glue one specific pair together everywhere it appears. This is the "hands" of BPE: count_pairs decides what to glue, and merge does the gluing.

Goes in

A list of IDs, the pair to glue (two IDs), and the new ID to replace it with

→
Comes out

A new, shorter list in which every occurrence of the pair is now that single new ID

The goal

Rewrite the list so that a two-token pattern becomes one token. Every replacement turns two IDs into one, so the list gets one item shorter each time.

How it works: scan left to right

merge([1, 2, 3, 1, 2], pair (1, 2), new ID 99)

  1. Look at 1. Is it followed by 2? Yes, so write 99 and skip past both.
  2. Look at 3. Is it followed by 2? No, so copy 3 as it is.
  3. Look at 1. Followed by 2? Yes, so write 99 and skip both.
↓

Five items have become three.

No overlaps

Because it skips past both items after a match, a token can only be used once:

merge([1, 1, 1], (1, 1), 7) → [7, 1]

The first two 1s become 7. The third 1 has no partner left, so it stays.

A side effect: the neighbours change

Gluing one pair changes the counts of the pairs around it. Before the first merge, ␣ + t was the second most common pair at 2,906. Look at "the tree":

Before

contains the pair ␣ + t

→
After

the space now belongs to e␣, so ␣ + t is gone

Every time "e␣" swallowed a space that came right before a t, one ␣ + t disappeared. Its count drops to 2,516, which is below d + ␣ at 2,616. That's why the second merge is d␣ and not ␣t. This is why tok_train recounts after every merge instead of counting once up front.

merge only rewrites the list. It doesn't record anything about what the new ID means. Writing the rule in the rulebook and the new entry in the dictionary is tok_train's job. That makes merge reusable: tok_encode calls the same function to replay old rules on new text.

Function 5 of 7

tok_train

The learning loop. Count, pick the winner, glue it, write it down, and repeat until the vocabulary reaches the target size.

Goes in

A blank tokenizer, some training text (100,000 characters), and a target size (512)

→
Comes out

The same tokenizer, now filled with 256 merge rules and 512 dictionary entries

The goal

Discover the most useful chunks of text, the ones that will shorten the stories the most, and record how to build each one. This is the only part of BPE that learns. Everything afterwards just follows the rules it writes down.

One round of the loop

  1. Turn the text into bytes (only once, before the first round): 100,000 characters become 100,048 IDs.
  2. Count every neighbouring pair with count_pairs.
  3. Pick the pair with the highest count.
  4. Give it the next free ID, which equals the current size of the dictionary: 256 the first time, then 257, and so on.
  5. Glue that pair everywhere with merge.
  6. Write it down in two places: the rule "(e, ␣) → 256" goes in the rulebook, and "256 means the bytes of e followed by the bytes of ␣" goes in the dictionary.
  7. Is the dictionary at 512 yet? If not, go back to step 2. 512 − 256 = 256 rounds in total.

The order of the rules matters. Rule 13 (th + e␣ → the␣) only makes sense once rules 1 and 3 have already created e␣ and th. The rulebook keeps the rules in the order they were learned, so tok_encode can replay them in that same order.

Two details

  • It can stop early. If the text ever shrinks to a single token, there are no pairs left to count and the loop ends. With 100,000 characters of stories, that never happens.
  • The size is a choice. 512 is small so the model trains quickly. The full-size model in the book uses 4,096. A bigger vocabulary gives shorter sequences, but each token appears less often and is harder to learn.

Function 6 of 7

tok_encode

Use what was learned. Take any text, break it into bytes, then replay every rule in the rulebook, in order, to rebuild the learned chunks.

Goes in

A trained tokenizer and any text, such as "the cat"

→
Comes out

A list of token IDs, such as [268, 99, 388]

The goal

Turn text into the numbers the model reads, and do it the same way every time, so that "the␣" is always token 268 whether it shows up in training, in a prompt you type, or in a story the model has never seen.

How it transforms the input

It starts from bytes and runs through all 256 rules from first to last. Most rules don't match anything in a short text, so nothing happens. Here are the only four that change "the cat":

Start: 7 bytes

Rule 1: e + ␣ → 256

Rule 3: t + h → 258

Rule 13: th + e␣ → 268

Rule 133: a + t → 388

Result: [268, 99, 388], three tokens instead of seven. "c" never paired with anything common enough, so it stays a single byte.

More examples from the trained tokenizer

TextTokensWhat to notice
Once upon a time
Every story starts this way, so the phrase became one token. The final "e" is left over because rule 1 already glued "e" to the space after it, so training built the chunk from "tim". Add a space ("Once upon a time ") and you get [453, 256]: "Once upon a tim" + "e␣".
Tom lost his red ball.
Common words are whole tokens. Rarer ones like "lost" and "ball" are spelled from pieces.
hi
No rule covers "hi", so it stays as plain bytes.
é
Never seen in training, but it still encodes fine as its two raw bytes.

Why replay in order? Later rules are made from earlier ones. Rule 13 looks for the pair (258, 256). If you ran it before rules 1 and 3, those IDs wouldn't exist in the list yet and it would find nothing. Replaying in the order learned rebuilds the chunks the same way training built them.

Where its output goes

The whole million-character book goes through tok_encode, and the resulting list of IDs is all the model ever sees. 90% of it is used for learning and 10% is held back for testing. Your prompts go through the same function when the model writes a story.

Function 7 of 7

tok_decode

The way back. Turn a list of token IDs into readable text by looking up what each ID stands for and joining the pieces.

Goes in

A trained tokenizer and a list of IDs, such as [268, 99, 388]

→
Comes out

Text: "the cat"

The goal

The model thinks in IDs and writes in IDs. tok_decode turns its output back into words a person can read.

How it transforms the input

It takes two simple steps and doesn't use the rulebook at all, only the dictionary:

  1. Look up each ID's bytes and join them end to end.
  2. Read those bytes as UTF-8 text.

IDs

Look up each one in the dictionary

Join the bytes

Read as text: "the cat"

Why decoding is easy and encoding is not

The dictionary already stores the full bytes for every token. Training wrote "the␣" as its complete bytes, not as "th + e␣". So decoding is a straight lookup with no replaying and no ordering. Encoding has to work out which chunks to build, so it needs the whole rulebook.

A round trip always gets you back where you started. Encode any text, decode the result, and you get the exact same text, including capitals, punctuation, spaces, and line breaks. Nothing is lost, because every token is just a shorthand for specific bytes.

One safety net: broken characters

Some characters take more than one byte. For example, "é" is the bytes 195 then 169. When the model generates text one token at a time, it could produce a 195 without the 169 that should follow it. Those bytes aren't valid text on their own.

Instead of crashing, tok_decode swaps any broken piece for the replacement mark � and keeps going.

Where it's used

At the very end of the GPT (step 21). The model looks at the IDs so far, picks the next ID, adds it to the list, and repeats. When it's done, tok_decode turns the whole list into a story you can read.

The full cycle

text → tok_encode → IDs → the model → more IDs → tok_decode → text
