Backprop Rules

Backprop sounds scary, but the whole backward pass in main6.py is built out of three tiny rules, used over and over. This page walks through what a gradient is, how blame gets passed back down the line, and why we had to save all those caches.

The three rules (the same ones at the top of the backward pass):

y = a + b      a and b both get the full gradient of y
y = x * w      x gets  (gradient of y) * w      w gets  (gradient of y) * x
y = x @ w      x gets  (gradient of y) @ w.T    w gets  x.T @ (gradient of y)

By the end you should be able to see where each one comes from, and check them yourself with a nudge.

1. What a gradient actually is

A gradient answers one question about one number: "if I nudge you up a tiny bit, how much does the loss move?" If the loss goes up 3 times as much as the nudge, the gradient is 3. If it goes down, the gradient is negative.

That's it. The gradient of a weight is its blame. Training then moves every number a little bit the opposite way of its gradient, which is downhill, so the loss shrinks.

A tiny "model" with one number in it: loss = (w − 3)². The best w is 3, where the loss is 0.

Notice: when w is too big the gradient is positive (so "minus the gradient" pulls w down), and when w is too small it's negative (pulls w up). The further from 3, the bigger the push.

2. The chain rule: passing blame back down the line

A real model isn't one step, it's a long chain of steps. Here's a short chain. Forward goes left to right:

x  →  a = x * 3  →  b = a + 4  →  loss = b * b

Backward goes right to left. Each step only needs to know its own little rule plus the gradient handed to it from the step after it. It multiplies them and hands the result back.

This is exactly what backward() does, just with way more steps: start with the gradient of the loss, then each step turns "gradient of my output" into "gradient of my input" and passes it back.

3. The three rules, with numbers

y = a + b

Both get the full gradient of y. Nudge a up by 0.001, and y goes up by exactly 0.001. Same for b. So whatever blame y has, a and b each get all of it.

a = 2, b = 5, y = 7. Gradient of y handed down: 0.3
→ a gets 0.3, b gets 0.3

This is the residual: vectors = vectors + attention_output. The gradient goes straight down to the vectors below and into attention, untouched. That's the "straight path back through every block" that lets deep models train.

y = x * w

Each gets the gradient times the other one. Nudge x up by 0.001 and y goes up by 0.001 × w. So x's blame is scaled by w, and w's blame is scaled by x.

x = 2, w = 5, y = 10. Gradient of y: 0.3
→ x gets 0.3 × 5 = 1.5, w gets 0.3 × 2 = 0.6

This is why caches exist. To work out w's gradient you need to know what x was. By the time backward runs, forward is long over, so forward had to save x.

y = x @ w

Just the multiply rule plus the add rule, done for every entry at once. A matrix multiply is a pile of "multiply pairs, add them up". Section 4 shows it number by number.

x gets (gradient of y) @ w.T
w gets x.T @ (gradient of y)

This one is every linear in the model, plus the two attention multiplies.

4. Where the matrix rule comes from

Take a token with 2 numbers, x (1×2), and a weights matrix w (2×2). Pretend the rest of the model turns y into a loss like loss = 0.1·y₁ − 0.2·y₂, so the gradient handed down to y is [0.1, −0.2]. Change any number and everything updates.

Gradient for x: (gradient of y) @ w.T

x₁ shows up in both outputs: in y₁ multiplied by w₁₁, and in y₂ multiplied by w₁₂. Multiply rule for each one, then add rule to combine them. That "go across a row of w" pattern is exactly what @ w.T does.

Gradient for w: x.T @ (gradient of y)

Each weight only touches one output: w₁₁ is only in y₁, multiplied by x₁. So its gradient is just (gradient of y₁) × x₁. Doing that for every weight makes a grid the same shape as w, which is exactly x.T @ (gradient of y).

Check it with a nudge

The shape trick. If you forget which side the transpose goes on, use the shapes. The gradient of a thing always has the same shape as the thing. In the model, x is (64, 128), w is (128, 384), and y is (64, 384). The only way to make a (128, 384) out of x and the gradient of y is x.T @ grad_y: (128, 64) @ (64, 384). The only way to make (64, 128) is grad_y @ w.T: (64, 384) @ (384, 128). The shapes force the answer.

One more thing the shapes give you for free: in x.T @ grad_y, the 64 in the middle gets summed away. That's the 64 tokens. Every token used the same weights, so each weight's blame is the total from all 64 tokens. Same reason bias_gradient = gradient.sum(axis=0).

5. Why we saved the caches

Every rule that multiplies needs to know what was on the other side. Plain adds and reshapes don't. So the caches are exactly the "other side" for every multiply in the model:

"qkv", "output", "expand", "shrink", head_cachethe vectors that went in + the weightsy = x @ w: weights need x, x needs w
"layer_norm", "layer_norm2", final_cachenormalized, spread, scalescale multiplied normalized, and dividing by spread has to be undone

"queries", "keys"the heads' queries and keysscores = queries @ keys.T

And the things with no cache: the residual adds (rule 1, gradient just copies), the reshapes and transposes (gradient just gets shuffled back the same way), and the hide-the-future mask (those spots had weight 0, so they get 0 gradient on their own).

6. In your code

linear_backward is rule 3, word for word:

def linear_backward(gradient, cache):
    vectors, weights = cache                  # what forward saved
    vectors_gradient = gradient @ weights.T   # x gets (gradient of y) @ w.T
    weights_gradient = vectors.T @ gradient   # w gets x.T @ (gradient of y)
    bias_gradient = gradient.sum(axis=0)      # bias was added to all 64 tokens (rule 1), so add up their blame
    return vectors_gradient, weights_gradient, bias_gradient

And the residuals are rule 1:

gradient = gradient + mlp_gradient         # the + in forward split into two paths, they join back up here

Attention uses rule 3 twice more, with the heads as an extra dimension in front:

#forward:  gathered = weights @ values
weights_gradient = attention_gradient @ values.transpose(0, 2, 1)   # (gradient of y) @ w.T
values_gradient  = weights.transpose(0, 2, 1) @ attention_gradient  # x.T @ (gradient of y)

7. Why can't it learn the learning rate too?

Backprop only finds gradients for numbers that are used in the forward pass, because a gradient means "if this number changed, how would the loss change?" The learning rate never shows up in forward. Making a guess about the next token doesn't use it at all. Change the learning rate and the loss for this guess stays exactly the same, so its gradient is 0. Backprop can't see it.

The learning rate is a rule about training, not part of the model. It answers a question the gradient can't: the gradient tells you which way is downhill right where you're standing, but not how far the hill keeps going that way. Step too far and you overshoot (that's the 0.5 run in main6.py jumping from 4.5 up to 6.2). Step too little and training takes forever.

People have tried learning it anyway, and the best ideas partly do:

  • Adam (what main3.py uses) gives every single number its own step size, based on how big its recent gradients have been. So it does adjust, a lot, on its own. But it still needs one overall learning rate on top.
  • Schedules change the learning rate over time on purpose: start small, ramp up, then slowly shrink so the end is fine-tuning.
  • There are research methods that estimate a gradient for the learning rate by looking at how the last step went. They exist, but they need their own step size for that, so you're back to picking a number. It's knobs all the way up, and in practice picking a good learning rate by trying a few is easier.

So the honest answer: it's not part of the guess, so backprop can't touch it, and the tricks that tune it automatically still leave one number for you to pick.
